# PetCare AI 需求与验收基线

> 状态：总体需求与验收基线已确定；框架基线采用 Java 21、Spring Boot 4.1.1、Spring AI 2.0.1，不保留 Spring Boot 3.5 兼容要求。M0 的依赖解析、启动探针、MySQL 8.4/Testcontainers 与 Flyway V1/V2 数据库门槛已通过；M0 前端、OpenAPI、CI、Compose 尚未完成。M1 后端已完成注册/登录/JWT、本人资料和宠物创建/列表/详情子切片；logout、宠物修改/归档及其他业务仍待实现。日期：2026-10-08。

## 1. 目标、非目标与版本范围

PetCare AI 为养猫、养狗等个人用户提供桌面优先、可响应式使用的健康记录网站。V1 以可信、可追溯的日常记录、消费统计、数据隔离和可部署为核心；AI 只在核心业务稳定后作为只读总结功能加入。

明确不做：原生 App、诊断/处方/剂量推荐、图片或语音分析、商城、微服务、Spring Cloud、Kubernetes、Kafka、多 Agent、向量数据库、模型训练、复杂工作流；邮箱/短信/微信通知、手机号认证、找回密码及退款/多币种也不属于首版。

| 版本 | 功能范围 | 验收重点 |
|---|---|---|
| P0 / M1 | 用户注册、登录、退出、个人资料/改密；多宠物档案；每日健康记录；体重；消费；单宠物基础 Dashboard；用户数据隔离 | 正常闭环、空数据、重复/非法输入、A/B 越权、统计一致性、关键 E2E、Compose 冒烟 |
| P1 / M2 | 疫苗、驱虫、就医及关联费用；站内到期提醒；完整 Dashboard；基础管理员聚合视图 | 日期边界、关联费用事务、归属校验、管理员权限边界 |
| P2 / M3–M4 | 经同意启用的只读 AI、会话及调用元数据；手动健康周报、历史快照，之后再加每周调度 | Tool 授权、缺失数据/故障降级、提示注入、周报并发幂等与恢复 |

## 2. 用户主流程与逐项验收

| 流程 | 可验收场景（包括空数据与异常） |
|---|---|
| 注册 / 登录 / 退出 | 新用户名创建 USER；重复规范化用户名返回冲突；错误密码不泄露账号是否存在；未登录访问私有接口返回 401；退出后旧 Token 被服务端拒绝。用户名和密码必填，邮箱选填且不标记为已验证。 |
| 宠物档案 | 用户建立、查看、修改多只宠物并切换；出生日期可未知；空列表显示创建引导；畸形日期、无效枚举和超长字段被拒绝；伪造别人的 petId 不返回其数据。归档宠物不出现在默认选择列表，但其历史可在归档视图查看。 |
| 每日健康 | 每只宠物每天最多一条，可查看、编辑、删除；当天无记录显示“未记录”，不能显示成“正常”；UNKNOWN 是明确未知值；异常为真时必须填写异常描述；同宠物同日重复创建返回 409。 |
| 体重 | 支持补录、修改、删除和一天多次测量；最近值从记录实时派生；相同时刻按记录 id 作稳定次序；kg 与有效范围校验；空历史不生成虚构最近体重或趋势。 |
| 消费 | 每条支出归属一只本人宠物；支持分类、日期、金额、商家和描述的创建、修改、删除、筛选；金额只能为正 CNY 两位小数；跨宠物更新、负数、零值、无效分类拒绝；列表为空时统计为 0 且 UI 显示无记录。 |
| Dashboard | 必须选择一只有效宠物；呈现最近状态、体重、支出及趋势；缺失的健康/体重数据明确显示“未记录”；无疫苗/驱虫计划与到期状态仅在 P1 提供；宠物不存在或不属于本人按 404 隐藏资源存在性。 |
| 疫苗 / 驱虫（P1） | 支持历史、用户/兽医登记的下次日期、无计划状态；“即将到期”推荐边界为业务时区今天至未来 30 天（含今天和第 30 天），“已逾期”为早于今天，“无计划”为下次日期为空；不推断医学周期。 |
| 就医及费用（P1） | 就医可选关联一条费用；建立/修改/删除关联在一个事务内保持一致；金额统计只读费用记录；故障回滚不得留下孤立或重复费用。就医和费用宠物不一致时拒绝。 |
| AI 助手（P2） | 用户明确同意后才向外部模型发送最少必要数据；查询只针对已授权宠物；同名/指代不清时要求选择；无记录、Tool 故障、模型超时都如实说明，不以猜测补齐；禁止诊断/处方。无同意或 AI 关闭时普通记录功能照常工作。 |
| 周报（P2） | 手动生成上一个完整自然周报告，范围为周一 00:00 至下周一 00:00（Asia/Shanghai，左闭右开）；重复请求返回同一份正式报告；报告保留生成时统计快照；无数据、生成中、失败、成功状态可区分。 |
| 管理视图（P1/P2） | USER 不能调用管理接口；管理员只看聚合统计、调用元数据与脱敏事件，不看完整私聊或医疗备注；管理员不因此自动获得普通用户私有记录读取权。 |

## 3. 业务规则与暂定口径

- **时间：**业务日期使用 `YYYY-MM-DD`，Asia/Shanghai；“本月”和“最近 7 天”按该时区计算。技术时间 UTC 存储和传输，统一 ISO-8601 格式。
- **健康记录：**每日一条；枚举值包含 `UNKNOWN`。异常标记为真必须有描述；为假时描述置空。缺行表示未记录，不是健康正常。
- **体重：**kg，DECIMAL/BigDecimal，建议有效区间 `0.001–500.000 kg`。最近值按 `measured_at DESC, id DESC` 派生，不另存会漂移的快照。
- **支出：**CNY，DECIMAL/BigDecimal，建议单笔 `0.01–99999999.99`；只记录正数支出。费用统计唯一来源为 `expense_record`。
- **分页与边界：**默认 page=1、size=20，最大 100；稳定默认排序为时间倒序再 id 倒序；日期起止均闭区间对外输入，内部转换为业务时区区间；白名单字段排序。文本长度、枚举、数字范围进入 DTO 校验及数据库约束。
- **用户和唯一性：**用户名去首尾空格、仅允许 ASCII 字母/数字/下划线并统一小写保存；长度 4–32；数据库唯一索引兜底。邮箱是普通资料字段，不验证、不用于登录。
- **删除：**日常删除宠物默认为“归档”，历史仍可在归档档案内查看并且历史消费仍保留在账户总支出中；用户显式执行永久删除时，在事务中清除该宠物及其健康、体重、消费和后续关联的就医/对话/报告数据，再删除宠物。数据库外部键采用 RESTRICT，由服务按依赖顺序删除，防止误级联。记录表不套通用逻辑删除列，避免健康记录按日唯一键被软删除占用。
- **未来报告：**每宠物、每业务周默认一份正式报告，`(pet_id, period_start)` 唯一；失败重试更新同一报告并增加尝试元数据；显式重新生成规则需在 M4 定义，不静默改写历史快照。
- **权限：**请求 DTO 不接受 `userId`、`role` 等服务端字段。每个对象级接口都验证当前用户 → 宠物 → 记录的完整归属链；陌生用户的对象按 404 处理以避免存在性泄露。
